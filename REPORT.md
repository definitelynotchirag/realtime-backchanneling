## 2. Critical findings, ranked

### F1 — The committed benchmark report is synthetic, and it is what the UI displays
`outputs/benchmark-report.json` declares its own provenance:

```json
"source": "deterministic-policy-replay",
"provenance": { "kind": "synthetic_replay", "label": "Deterministic policy replay",
                "note": "Policy smoke timings only; no STT, LLM, or TTS provider was called.",
                "provider_latency_available": false }
```

The API returns that file as the **primary** report and only nests the real measurement underneath
(`src/blue_machines_baseline/api.py:84-96` — `primary["live_observation"] = _add_provenance(actual_report)`).
The dashboard declares `live_observation` as a type (`dashboard/app/page.tsx:54`) and **never renders it**.
Consequence: the grader opens the UI and sees replay numbers labelled at panel level, with no per-cell provenance, while the real observation is silently discarded. README.md:162-165 honestly warns about this; the UI does not enforce it.

### F2 — The replay does not exercise the policy, and is constructed so backchanneling looks faster
`benchmark.py` imports only stdlib — it never imports `BackchannelEngine` or `JevClassifier`. Cue counts are hard-coded per (scenario, mode) at `benchmark.py:582-602`, and the response model is a hard-coded per-mode offset:

- `benchmark.py:657` → `response_start = end + (510 if baseline else 500) + U(-35,45)`
- `benchmark.py:651` → LLM TTFT base `0.42` (baseline) vs `0.44` (others)
- `benchmark.py:554` → RNG seed **includes the mode**, so jitter is independent per arm, not common-random-numbers.

So the published deltas (−13.5 ms timer, −21.2 ms Jev) are smaller than the ±35–45 ms jitter they are drawn from, and the "backchannel is faster" result is an artifact of the generator. This is the single most damaging finding for the "Benchmarking and latency analysis (20%)" criterion.

### F3 — Real provider data exists but was never aggregated, and is not a fair comparison
`outputs/baseline-events.jsonl` (6.8 MB) contains **real** room sessions in all three modes with genuine provider metrics. I ran the shipped analyzer over it (`uv run blue-machines-benchmark --events outputs/baseline-events.jsonl --report /tmp/real-report.json`) — it does produce a `provider_event_log` report, but the numbers are not usable:

| Metric (shipped analyzer, real log) | Baseline | Backchannel (timer) | Jev |
|---|---|---|---|
| Response P50 | 107 410 ms *(n=18)* | 32 999 ms *(n=44)* | 67 491 ms *(n=100)* |
| Response P95 | 443 483 ms | 187 570 ms | 332 930 ms |
| LLM TTFT P50 | 2 015 ms | 2 027 ms | 1 943 ms |
| TTS TTFB P50 | 428 ms | 445 ms | 438 ms |
| Backchannel P50 | — | 8.2 ms | 1 041 ms |
| Backchannels / cancelled / EOT-risk | 50 / 52 / 6 | 80 / 59 / 16 | 156 / 82 / 16 |

A "107 second" baseline response latency is not a measurement, it is a pairing bug: `summarize_run` pairs **each** `user_speech_ended` with the **next** `agent_response_started` globally (`benchmark.py:252-265`). In multi-turn sessions where a turn produces no logged response, the cursor drifts and swallows idle time. This also breaks `baseline` sessions that emit 50 backchannel events — the mode labels in the log are internally inconsistent.

Coverage is also wrong for the assignment: only **3 of 8 scenarios** have real runs (`short_answer`, `long_monologue`, `approaching_end_of_turn`), and they are not paired per mode:

### F4 — EOT signal is a final-transcript heuristic; the threshold is dead code
`src/blue_machines_baseline/agent.py:310-315` documents it and calls `engine.update_eot_probability(1.0)` on a final transcript while the user is silent. That is the **only** call site. `eot_threshold = 0.8` (`backchannel.py:37`) can never discriminate because the policy only ever sees `1.0` or `None`. The assignment explicitly lists "end-of-turn probability" as a signal to consider; what ships is a binary proxy. (The SDK does compute a real EOT internally but exposes it only on a non-public event — the README documents this, but no alternative such as using the public `inference.TurnDetector` was attempted or recorded as rejected.)

## 3. What is genuinely well done

1. **Engine race discipline.** At most one timer task (`backchannel.py:220`), generation counter stamped into the task and re-checked at fire time (`backchannel.py:235`, `263`) and again after playback start (`backchannel.py:295-301`); every state change funnels through `_cancel_pending`/`_interrupt_active`. Cancel triggers: user floor change, real-agent busy, runtime disable, shutdown, post-play race re-check — all five present.
2. **Honest latency anchors.** Both headline anchors are real audible-playback markers, not handle creation: the agent response start derives from LiveKit's output `playback_started` (via `agent_state_changed`, `agent.py:201-207`), and the backchannel's audible start comes from `session.output.audio.on("playback_started")` → `mark_audio_started()` (`agent.py:377-380`, `backchannel.py:191-196`). Recorded evidence shows why this matters: 425.99 ms decision→audible vs 1.27 ms decision→handle.
3. **Context isolation.** `add_to_chat_ctx=False` (`agent.py:261`) and the ack's speaking transition is labelled `backchannel_agent_speaking` instead of `agent_response_started` (`agent.py:201-205`), so it is excluded from both conversation history and the response metric.
4. **No private LiveKit APIs.** All LiveKit imports are public modules; the handle is duck-typed (`getattr(handle, "done", None)`) rather than reaching into internals. LiveKit is a pinned dependency, not vendored or patched.
5. **Jev is off the critical path and fails closed.** Timeouts, errors, stale results, final transcripts and user-stops all resolve to "no cue" (`jev.py:316-346`); nothing in the reply pipeline awaits it.
6. **Cached backchannel audio is real.** Three pre-rendered WAVs loaded per process and passed to `session.say(..., audio=...)` (`agent.py:27-49`, `263-264`), with a live-TTS fallback when a clip is absent.
7. **Tests are behaviour-first, not utility-only.** 63 tests, all passing, covering all nine required cases — including `test_livekit_hook_keeps_backchannel_out_of_chat_context` (`tests/test_backchannel.py:366`), `test_shutdown_interrupts_active_acknowledgement_and_prevents_late_playback` (`:283`), `test_failed_tts_playback_does_not_leave_policy_stuck` (`:234`), `test_rapid_floor_transitions_leave_only_the_latest_turn_eligible` (`:258`).

## 5. Minimum work to close the gap

Priority order — the first three are what the assignment actually grades:

1. **Generate and commit a real report.** Fix the pairing in `summarize_run` (pair within a turn/`speech_id`, bound the search window, drop unpaired turns), then produce `outputs/benchmark-report-provider.json` from labelled sessions and make the API/UI prefer it over the replay. Render `live_observation` or replace the primary report outright.
2. **Get real runs for all 8 scenarios, ~5 repeats, paired per scenario.** Nothing else in the "20% benchmarking" bucket is credible until baseline and backchannel run the *same* scenario with the *same* scripted speech. A synthetic audio participant would also satisfy "do not depend only on manually speaking into the microphone twice".
3. **Write the missing reasoning.** A "bad backchannel" definition with thresholds and justification; what got slower and where the extra latency came from; the production-scale section; then fix the three falsified README claims.
4. **Add the three missing behaviour metrics** (per-long-turn ratio, per-cue attribution of response delay, audible-cue count) and make `end_of_turn_risks` non-zero by emitting `backchannel_collision`, or delete the dead counter.
5. **Close the race hazard and the open defect:** a cue played with `allow_interruptions=False` can cause LiveKit to **drop the user's turn entirely** (`agent_activity.py:2774-2779`); close the residual window where the cue is interrupted but not yet cleared, and add the one-cue-one-audio-stream regression test the handover defers.
6. **UI:** render the overall aggregate, tag every cell with its provenance, overlay baseline vs backchannel for one scenario, and give timeline events distinct styles/durations.
7. **Init a git repo and commit.** `outputs/*.jsonl` must be committed (or summarized) or the only evidence that ships is the synthetic file.
8. **Optional but cheap wins:** feed `eot_inference_metrics.detection_delay` into the policy (it is already captured at `agent.py:76-78`, just never consumed), use the VAD-backdated `event.created_at` for `user_speech_ended` so absolute latencies stop being understated, and add repeat-based variance so a 30 ms delta can be distinguished from noise.

### What the real runs are, and what they are not

The sweep drives every scenario in **baseline** and **timer backchannel** mode, three
repeats each, through real LiveKit rooms with real Groq STT, Gemini LLM and Gemini TTS.
The committed evidence is `outputs/benchmark-events.jsonl` (the scripted runs extracted
from the worker's log) and the report built from it,
`outputs/benchmark-report-provider.json` — 35 runs, four scenarios, both arms for three of
them.

**Measured outcome (baseline → timer backchannel), now on a single all-Groq stack:**
response P50 1276 ms → 781 ms (n=13/12, σ 1.58 s → 0.63 s), P95 4407 ms → 1949 ms, audible
cues 0 → 11, cues per long turn 0.00 → 0.89, cue decision→audible 1.5 ms, LLM TTFT and TTS
TTFB identical within 5 ms across arms, and **0 delayed responses and 0 collisions in both
arms** (one cancelled cue). No measurable slowdown, and no turn-taking damage in the sample.
The UI shows the same numbers.

Three limits are stated rather than hidden:

1. **The sweep stopped early: the speech provider's daily budget ran out.** Orpheus on the
   free tier allows 3600 speech tokens/day (~70 short utterances) and the sweep spent it, so
   `noisy_audio`, `multiple_backchannels` and `stop_before_ack` have no measured runs. n is
   12-13 per arm — enough for a P50 with a reported σ, not for a trustworthy P95. Scripted
   runs now skip the greeting to halve the budget per sweep, and the driver aborts after
   three consecutive silent runs instead of recording provider failures as data.
2. **Jev mode is not in the sweep, but it runs.** Jev needs interim transcripts, so a new
   `groq_interim` provider transcribes Groq's batch endpoint on a cadence and emits partial
   transcripts while the user speaks (verified: seven interims during an 8.8 s utterance).
   A real Jev run produces the full semantic path - interim transcript, `jev_request_started`,
   `backchannel_semantic_approved`, `jev_decision {approved: true, confidence: 0.92}`, then a
   638 ms cue - but including it in the sweep needs speech budget for two more arms.
3. **The TTS used for the sweep is non-streaming**, so the agent cannot start speaking
   until the whole utterance is synthesised (~2.8 s, measured). That cost lands on both
   arms equally, which keeps the *comparison* fair while inflating absolute latency. A
   production deployment would use a streaming provider; the README says so.
